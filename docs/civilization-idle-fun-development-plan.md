# Civilization Idle: แผนพัฒนาให้เล่นสนุกขึ้น

สถานะ: ข้อเสนอเพื่อทดลอง ไม่ใช่การเปลี่ยนกติกาที่อนุมัติแล้ว | 25 พฤศจิกายน 2026

## เป้าหมาย

ทำให้ผู้เล่นรู้เสมอว่า **ทำอะไรต่อ**, เห็นผลของการตัดสินใจจัดคนงาน/วิจัย/โรงงาน และกลับมาเล่นครั้งถัดไปเพราะมีเป้าหมายใหม่ ไม่ใช่เพียงรอเลขเพิ่ม เกมยังเป็นเมืองส่วนตัวของนักเรียน ไม่ผูกคะแนนหรือ Gold, ไม่แข่งขันจัดอันดับ และไม่บังคับเข้าเกมทุกวัน

ตารางนี้เป็น **แรงบันดาลใจเชิงออกแบบ** ไม่ใช่หลักฐานว่าฟีเจอร์ดังกล่าวจะเพิ่มความสนุกในกลุ่มนักเรียนของเรา ต้องยืนยันด้วย playtest ก่อนผลิตเต็มระบบ

## สภาพเกมปัจจุบันและช่องว่าง

- วงจรที่มีแล้ว: เก็บทรัพยากร -> สร้างอาคาร -> จัดคนงาน -> สะสม Science -> วิจัย -> ยุคสำริด -> โรงงาน -> Steam Power; Phase 1 เพิ่ม offline สูงสุดเป็น 72 ชั่วโมงและยังใช้ server-authoritative save
- เพิ่งเพิ่มข้อความผลวิจัยและเปิดอัปเกรดโรงงานจาก `count` ที่ engine รองรับอยู่แล้ว; งานเหล่านี้ยังเป็นการเปลี่ยนแปลงใน worktree **ยังไม่ commit/deploy** อย่าวางแผนราวกับผู้ใช้ production เห็นแล้ว
- UI ยังขาดภาพรวมอัตรา **สุทธิ** และเหตุผลที่การผลิตหยุด เช่น อาหารประชากร, input ไม่พอ, output เต็ม; ตัวเลขผลผลิตรวมบนการ์ดไม่เท่ากับผลผลิตจริงเมื่อ converter หยุดเพราะข้อจำกัด
- หลังถึง Steam Power ไม่มีเป้าหมายเล่นต่อ; แต่ไม่ควรรีบเพิ่มยุคใหม่ก่อนทดสอบว่าช่วง Stone/Bronze สนุกและเล่นจบได้จริง
- ยังไม่มีข้อมูลระยะเวลาถึง milestone, จุดเลิกเล่น หรือข้อเสนอแนะจากนักเรียน จึงห้ามตั้งค่าต้นทุน/เวลาว่าเหมาะสมแล้ว

## หลักออกแบบ

1. **ทางเลือกมากกว่างานกดซ้ำ:** กิจกรรมกดเองช่วยแก้คอขวดได้ แต่เส้นทางหลักควรชนะด้วยการตัดสินใจจัดงานและลงทุน
2. **Feedback ตรงกับ simulation:** บอก gross, consumption, net, cap, และเหตุผลที่โรงงานไม่ผลิต; ค่า UI ต้องใช้สูตรเดียวกับ engine
3. **ความคืบหน้าสั้นและยาว:** มีเป้าหมายใกล้ 1 ขั้นและเป้าหมายปลายยุค โดยเปิดเผย prerequisite และต้นทุน
4. **ล้มเหลวแล้วกู้ได้:** อาหารหมดไม่ลบเมือง; มีทางกลับด้วย manual action และคำแนะนำ ไม่ทำ softlock
5. **เหมาะกับห้องเรียน:** ไม่มี FOMO, pay-to-win, daily streak ที่ลงโทษ, PvP หรือการแปลงเป็นคะแนน/รางวัลการเรียนโดยอัตโนมัติ
6. **เซฟเดิมต้องอยู่:** เพิ่มเนื้อหาผ่าน catalog/derived UI ก่อน; ถ้าเพิ่ม field ให้ version snapshot และ migration ที่ทดสอบย้อนหลัง

## ลำดับพัฒนา

### Phase A: ความชัดเจนและความเชื่อมั่น (P0)

- เพิ่ม resource detail: ผลิตจากคนงาน/โรงงาน, ใช้โดยประชากร/โรงงาน, **สุทธิต่อวินาที**, เวลาโดยประมาณจนเต็มหรือหมด (แสดงเฉพาะเมื่อคำนวณได้จริง)
- แสดงสถานะโรงงาน `กำลังผลิต / วัตถุดิบไม่พอ / คลังเต็ม / หยุดเอง` จากกติกาจำลองเดียวกัน; แยก “กำลังผลิตตามทฤษฎี” จาก “ผลิตได้ตอนนี้”
- เพิ่มตัวชี้เป้าหมายถัดไป: เช่น สร้างลานเล่านิทาน -> มีนักปราชญ์ -> Science 10 -> เครื่องมือพื้นฐาน; ระบุสิ่งที่ขาดและปุ่มไปแท็บที่เกี่ยวข้อง
- เพิ่ม feedback หลังลงทุน: ต้นทุนที่จ่าย, อัตราก่อน/หลัง, event log เป็นภาษาคน; ไม่เพิ่มข้อมูลลับหรือเสียงรบกวนห้องเรียน
- จุดแก้หลัก: `src/lib/civilization-idle/simulation.ts`, `content.ts`, `src/components/civilization-idle/civilization-game.tsx`, `civilization-copy.ts`
- เกณฑ์ผ่าน: ตัวเลข UI ตรง engine ในสถานะปกติ/อดอาหาร/คลังเต็ม/วัตถุดิบหมด/โรงงานหยุด; มือถือ 390px ไม่มีล้นแนวนอน; คำแปล TH/EN ครบ

### Phase B: ภารกิจและ milestone (P1)

- ทำ **guided goals แบบเลือกได้** 6-8 ขั้นในยุคหินและ 4-6 ขั้นในยุคสำริด เช่น มอบหมายคนหาอาหาร, รักษาสุทธิอาหาร, สร้างแหล่ง Science, วิจัยเกษตรกรรม, ถลุงทองแดง, ผลิตสำริด, Steam Power
- แต่ละเป้าหมายมีเงื่อนไขจาก state ที่ตรวจซ้ำได้; แสดงความคืบหน้าและประโยชน์ของการทำ ไม่แจกทรัพยากรที่ทำให้ balance เปลี่ยนในรอบแรก
- milestone เป็น cosmetic/บันทึกประวัติเมืองส่วนตัว; หลีกเลี่ยงข้อความสื่อว่าผู้เรียนเก่ง/อ่อนตามความเร็วเกม
- ข้อมูลเป้าหมายเป็น catalog แยกจาก engine; `completed` อนุมานจาก state เมื่อได้ หากต้องเก็บการรับรางวัล/เลือกภารกิจจึงค่อยเพิ่ม schema
- เกณฑ์ผ่าน: เซฟเก่ามองเห็น milestone ที่เคยทำ, ไม่มีการรับซ้ำ, เปิดหน้าแล้วรู้เป้าหมายต่อไปภายในไม่กี่วินาทีจากการสังเกต playtest

### Phase C: ทางเลือกเชิงกลยุทธ์ (P1 หลัง B)

- ทดลอง **นโยบายเมือง 2-3 แบบที่สลับได้** เช่น อาหารมากขึ้นแต่ Science ช้าลง / เน้นความรู้แต่ใช้ไม้เพิ่ม; เริ่มด้วยตัวคูณเล็กและโปร่งใส ไม่เพิ่ม RNG ในเศรษฐกิจหลัก
- ให้ผู้เล่นเปรียบเทียบผลสุทธิก่อนยืนยันนโยบาย; สลับได้โดยมี cooldown ฝั่ง server ที่เหมาะสม ไม่เสียทรัพยากรหากกดผิด
- สำรวจทางเลือกการจัดโรงงาน: เปิด/หยุดรายชนิดที่มีอยู่ก่อน; หลีกเลี่ยง queue/automation ซับซ้อนจนกว่าจะรู้ว่าผู้เล่นเจอคอขวดจริง
- ตัวเลขนโยบายเป็น **สมมติฐาน balance** ต้องจำลองเส้นทาง Stone -> Bronze -> Steam Power และ playtest ก่อนล็อกค่า
- เกณฑ์ผ่าน: มีอย่างน้อยสองวิธีเดินเกมที่ใช้ได้จริงโดยไม่มีทางเลือกหนึ่งครองทุกสถานการณ์; ไม่เกิด resource ติดลบ, softlock หรือฟาร์มไม่จำกัด

### Phase D: เนื้อหาและบรรยากาศ (P2)

- เพิ่มเหตุการณ์เมืองสั้น ๆ ที่ผูก milestone/สถานะจริง ไม่สุ่มลงโทษหนัก เช่น ค้นพบแหล่งหินเมื่อสร้างเหมือง; ตัวเลือกมีผลจำกัดและมีข้อความชัดเจน
- เพิ่มภาพเมืองเปลี่ยนตาม milestone สำคัญ 2-3 จุดก่อนพิจารณาแผนที่หรือยุคใหม่; ภาพต้องสัมพันธ์กับความก้าวหน้าที่เกิดจริง
- หลัง pilot ยืนยัน pacing แล้วค่อยออกแบบยุคถัดไปในเอกสารกติกาใหม่: resource chain, science cap, conversion, migration และจุดจบที่เล่นได้; ไม่ปลดล็อก Industrial เพียงเพราะชื่อ Steam Power
- เกณฑ์ผ่าน: event ไม่ทำให้ผู้เล่นเสียความคืบหน้าแบบไม่คาดคิด, mobile โหลดได้เร็ว, asset มี fallback, ไม่ซ้ำจนรกหน้าจอ

## แผนวัดผลและ playtest

- ก่อนเริ่ม: ทำ baseline test route ของผู้เล่นใหม่ 5-8 คนใน staging (ไม่ใช้ production save), จับเวลาและจดจุดสะดุดโดยสมัครใจ
- ทดสอบรอบละ 10-15 นาที: (1) เข้าเกมใหม่และหาเป้าหมาย (2) จัดคนงานให้อาหารไม่ลด (3) สร้างแหล่ง Science (4) กลับมาเล่นหลังออกเกม; ถามว่าตัดสินใจอะไรและเพราะอะไร
- ตัวชี้วัด **เสนอเพื่อทดลอง ไม่ใช่ KPI บังคับ**: อย่างน้อย 80% บอกเป้าหมายถัดไปได้เอง, อย่างน้อย 80% อธิบายเหตุผลที่อาหาร/โรงงานหยุดได้, ไม่มีผู้เล่นติดค้างถาวร, ไม่มีข้อมูลเซฟเสีย
- เก็บเฉพาะ telemetry ขั้นต่ำที่ได้รับอนุมัติ: เวลา milestone แบบกลุ่ม, error command/sync, จุดที่ผู้เล่นเปิดคำแนะนำ; ไม่บันทึกชื่อ/รหัสนักเรียน, ไม่ทำ leaderboard, กำหนด retention และสิทธิ์เข้าถึงก่อนเก็บ
- หลังแต่ละ phase: เปรียบเทียบเวลาไปถึง Science, Agriculture, Bronze และ Steam Power; ตรวจว่ากลไกใหม่ลดความสับสนจริงหรือเพียงเพิ่มปุ่ม

## แนวทางเทคนิคและความปลอดภัย

- Engine ยังคง pure/deterministic, server ใช้เวลาและตรวจสิทธิ์; client ห้ามส่งยอดทรัพยากรที่คำนวณเองมาเขียนทับ
- เพิ่ม command ใหม่เฉพาะเมื่อจำเป็น พร้อม Zod schema, command receipt/idempotency, revision conflict handling, invariant, snapshot/content version และ migration ทดสอบย้อนกลับ
- ทดสอบ unit/property scenarios: อดอาหาร, วัตถุดิบขาด, output cap, offline 8 ชั่วโมง, command replay, สองแท็บชนกัน, เซฟเก่าเปิดหลัง deploy
- เปิดตาม feature flag และ pilot allowlist เดิม; backup staging ก่อน schema change, dark deploy, pilot, monitoring แล้วค่อยตัดสินใจ production; rollback ต้องไม่ลบเซฟ
- อย่าแก้ระบบคะแนน, Gold, LINE, Host/Play หรือฟิลด์เกมเก่าใน Student/Classroom ระหว่างเฟสนี้

## สิ่งที่ยังไม่ทำ

- Prestige/reset เมือง, daily streak, PvP, ranking, loot box, โฆษณา, การซื้อความเร็ว, บทลงโทษเมื่อไม่เข้าเกม
- ยุคใหม่/แผนที่/การค้า/สงครามจำนวนมากก่อนพิสูจน์วงจรสองยุคและต้นทุนการดูแลเนื้อหา

## งานแรกที่เริ่มได้ทันที

ทำ Phase A เฉพาะ **แผงอัตราทรัพยากรสุทธิ + เหตุผลที่โรงงานหยุด** พร้อม fixture ทดสอบ 5 สถานะ แล้ว playtest ให้ผู้เรียนอธิบายได้ว่าอาหารกำลังเพิ่มหรือลดเพราะอะไร งานนี้แก้ความสับสนที่พบจริงและเป็นฐานให้เป้าหมาย/นโยบายในเฟสถัดไป
