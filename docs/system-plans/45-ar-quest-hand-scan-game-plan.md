# แผนระบบเกม AR Quest แบบ Hand Scan

## เป้าหมาย

สร้างโหมดเกม AR สำหรับห้องเรียนที่เข้ากับระบบ Live Game เดิมของ GameEdu: ครูโฮสต์เกมจากชุดคำถาม นักเรียนเข้าด้วย PIN และหน้าเล่นใช้กล้องของอุปกรณ์ร่วมกับ hand tracking เพื่อเลือกคำตอบที่ลอยอยู่บนหน้าจอ

ช่วงแรกควรทำเป็น UI และ interaction prototype ก่อน จากนั้นค่อยต่อเป็น MVP ที่เชื่อม socket จริง ปุ่ม AR Quest ในหน้าเลือกโหมดจะยังเป็น "เร็ว ๆ นี้" จนกว่า engine และ flow กล้องฝั่งนักเรียนพร้อมใช้งาน

## Loop การเล่นหลัก

1. ครูเลือก **AR Quest** จากหน้าเลือกโหมดเกม
2. นักเรียนเข้าห้องผ่าน flow `/play` และ PIN เดียวกับ Gold Quest, Crypto Hack, Bingo และ Negamon Battle
3. หน้าเล่นของนักเรียนขอสิทธิ์กล้อง และเริ่มระบบจับมือ
4. ระบบแสดงโจทย์เป็น prompt ลอยบนภาพจากกล้อง
5. ตัวเลือกคำตอบลอยอยู่รอบ ๆ พื้นที่กล้อง
6. นักเรียนเลื่อนมือไปยังคำตอบ แล้วค้างมือหรือทำท่า pinch เพื่อล็อกคำตอบ
7. Server ตรวจคำตอบ อัปเดตคะแนน ความคืบหน้า และส่งโจทย์ถัดไป
8. เกมจบตามจำนวนข้อหรือเวลาที่กำหนด แล้วซิงก์รางวัลผ่านระบบคะแนน Live Game เดิม

## ขอบเขต MVP

- มีหน้า preview สำหรับ UI หน้าเล่น AR ที่ `/qa/ar-quest`
- มีตัวเลือกโหมดจอเล่น 2 แบบ: เล่นบนจอครู และเล่นบนจอนักเรียน
- Layout เป็นกล้องเต็มจอ มี HUD ด้านบน, โจทย์ลอย, ตัวเลือกคำตอบ, cursor มือ และสถานะด้านล่าง
- ใช้รูปแบบ question payload เดิมเท่าที่ทำได้: `id`, `question`, `options`, `timeLimit`, `image`
- ปุ่มในหน้า host selector ยังล็อกเป็น "เร็ว ๆ นี้" จนกว่าจะเพิ่ม backend mode support

## รูปแบบจอเล่น

ครูควรเลือกได้ก่อนเริ่มเกมว่า AR Quest จะเล่นบนจอไหน โดยเก็บค่าเป็น `playSurface`

### 1. เล่นบนจอครู (`teacher`)

เหมาะกับการเล่นหน้าห้อง หรือใช้โปรเจกเตอร์/ทีวีในห้องเรียน

- กล้องและ hand tracking ทำงานบนเครื่องครู
- นักเรียนผลัดกันออกมาหน้าห้องเพื่อใช้มือเลือกคำตอบ
- จอครูแสดงโจทย์ ตัวเลือก คะแนน และรายชื่อผู้เล่น
- นักเรียนที่เหลือดูจอรวมและรอลำดับของตัวเอง
- Server ยังเก็บคะแนนแยกตามนักเรียน โดยครูเลือกผู้เล่นปัจจุบันหรือใช้ลำดับคิวจากรายชื่อ

ข้อดี:

- เหมาะกับห้องที่นักเรียนไม่มีมือถือทุกคน
- ครูควบคุมจังหวะและความปลอดภัยได้ง่าย
- ใช้อุปกรณ์เพียงเครื่องเดียวก็เล่นได้

ข้อควรระวัง:

- ต้องมีระบบเลือกผู้เล่นปัจจุบันบนจอครู
- ต้องกันการตอบซ้ำเมื่อเด็กหลายคนอยู่หน้ากล้องพร้อมกัน

### 2. เล่นบนจอนักเรียน (`student`)

เหมาะกับการเล่นพร้อมกันหลายคนผ่านมือถือ แท็บเล็ต หรือ laptop ของนักเรียน

- กล้องและ hand tracking ทำงานบนเครื่องของนักเรียนแต่ละคน
- นักเรียนเห็นโจทย์และตัวเลือกบนจอของตัวเอง
- Server รับคำตอบจากแต่ละเครื่องผ่าน socket
- จอครูทำหน้าที่เป็น host dashboard, leaderboard และตัวควบคุมรอบ

ข้อดี:

- เล่นพร้อมกันได้ทั้งห้อง
- เก็บคะแนนรายบุคคลได้ตรงที่สุด
- เหมาะกับกิจกรรมแข่งขันแบบเร็ว

ข้อควรระวัง:

- ต้องขอสิทธิ์กล้องในเครื่องนักเรียนแต่ละเครื่อง
- ต้องมี fallback หากเครื่องบางเครื่องไม่รองรับกล้องหรือ hand tracking
- ต้องระวัง performance บนมือถือรุ่นเก่า

### ค่า setting ที่ควรเพิ่มในอนาคต

```ts
type ArQuestPlaySurface = "teacher" | "student"

type ArQuestSettings = {
  playSurface: ArQuestPlaySurface
  inputMode: "hand" | "tap-fallback"
  requireMarker: boolean
  turnMode: "all-at-once" | "queue"
}
```

## ออกแบบเชิงเทคนิค

### Client

- `src/components/game/ar-quest/ar-quest-play-preview.tsx`
  - เป็นต้นแบบ UI โดยใช้ภาพกล้องจำลองและสถานะ hand tracking จำลอง
  - ใช้ `useLanguage()` และ translation keys สำหรับข้อความที่ผู้ใช้เห็นทั้งหมด
  - ใช้ `framer-motion` สำหรับ animation เล็ก ๆ เช่น hand lock, answer focus และ feedback

### Hand Tracking ในเฟสถัดไป

- แนะนำใช้ MediaPipe Tasks Vision หรือ browser hand landmark model ที่ใกล้เคียง
- ประมวลผลบนเครื่องผู้ใช้เท่านั้น ไม่ส่งภาพจากกล้องขึ้น server
- แปลง hand landmarks ให้เป็นสถานะง่าย ๆ สำหรับเกม:
  - `open`: กำลังสแกน
  - `hover`: มืออยู่เหนือคำตอบ
  - `pinch`: ส่งคำตอบที่เลือก

### Server

เพิ่ม mode `AR_QUEST` ในอนาคตให้ทำงานร่วมกับ `PlayerMode` เดิม

Socket events ที่ควรมี:

- `submit-ar-answer`
- `ar-tracking-ready`
- `ar-marker-detected`
- `ar-round-result`

Engine state ที่ควรเก็บ:

- play surface: `teacher` หรือ `student`
- ลำดับโจทย์ปัจจุบัน
- คะแนนผู้เล่น
- streak
- marker id ที่ตรวจพบ ถ้ามี
- สถานะล็อกคำตอบ
- ผู้เล่นปัจจุบัน ถ้าใช้โหมดจอครูและ `turnMode: "queue"`

## แนวทาง UI

- กล้องต้องเป็นพื้นหลักของหน้าเล่น
- HUD ต้องสั้น กระชับ และใช้ glass panel เพื่อไม่บังภาพในห้อง
- ตัวเลือกคำตอบต้องเป็นเป้าขนาดใหญ่ วางห่างจาก prompt หลัก
- ด้านล่างแสดงเฉพาะสถานะจำเป็น เช่น กล้อง, มือ, การเชื่อมต่อ และคำแนะนำสั้น ๆ
- ข้อความฝั่งครูและนักเรียนใช้ชื่อ **AR Quest** ให้ตรงกับปุ่มโหมดเกม

## แผนทำงานเป็นเฟส

1. **UI Prototype**
   - เพิ่มหน้า `/qa/ar-quest`
   - ตรวจ layout บนมือถือและ desktop
   - ปรับ visual language จากภาพ reference ให้เข้ากับ GameEdu

2. **Local Camera**
   - เปลี่ยนพื้นหลังจำลองเป็น `<video>` จาก `getUserMedia`
   - เพิ่ม state ขอสิทธิ์กล้อง, กล้องถูกปฏิเสธ, โหลดไม่สำเร็จ และปุ่มลองใหม่
   - คง fallback ภาพจำลองไว้เมื่อกล้องยังไม่พร้อมหรือเปิดไม่สำเร็จ

3. **Hand Tracking**
   - เพิ่ม hand landmark model ฝั่ง client
   - map ตำแหน่งมือเป็น pointer บนหน้าจอ
   - เพิ่ม interaction แบบค้างมือหรือ pinch เพื่อส่งคำตอบ
   - ระหว่าง prototype ใช้ mouse/touch pointer เป็น fallback เพื่อทดสอบ hover, hold และ lock answer

4. **Live Game Engine**
   - เพิ่ม `AR_QUEST` เข้า host creation, player state, socket lifecycle และ game manager
   - เพิ่ม settings สำหรับ `playSurface`, `inputMode`, `requireMarker` และ `turnMode`
   - ใช้ระบบโหลดชุดคำถามและคิดคะแนนจากเกมเดิมให้มากที่สุด

5. **Classroom Rewards**
   - ซิงก์คะแนน, EXP หรือ gold ผ่านระบบ student identity และ classroom reward rules เดิม

## QA Checklist

- บนมือถือ HUD, โจทย์, ตัวเลือก และแถบล่างไม่ทับกัน
- ถ้าผู้ใช้ปฏิเสธสิทธิ์กล้อง ต้องมีข้อความที่เข้าใจง่ายและกู้คืนได้
- ข้อความตัวเลือกต้องไม่ล้นทั้งภาษาไทยและอังกฤษ
- cursor มือไม่บังโจทย์หลัก
- เล่นได้โดยไม่ต้องใช้ keyboard หรือ mouse
- โหมดจอครูต้องเลือกผู้เล่นปัจจุบันได้ และคะแนนเข้าผู้เล่นคนนั้นถูกต้อง
- โหมดจอนักเรียนต้องรับคำตอบพร้อมกันหลายเครื่องได้โดยไม่ชนกัน
- โหมดเกมเดิมยัง host และเล่นได้ตามปกติ

## สถานะ Local Camera

สิ่งที่ทำแล้ว:

- หน้าเล่น AR ใช้ `<video>` สำหรับกล้องจริงผ่าน `navigator.mediaDevices.getUserMedia`
- เมื่อเข้า play preview ระบบจะขอสิทธิ์กล้องอัตโนมัติ
- ถ้าเปิดกล้องสำเร็จ พื้นหลังหน้าเล่นจะเปลี่ยนเป็นภาพจากกล้องจริง
- ถ้ากล้องกำลังเปิด ถูกปฏิเสธ ไม่รองรับ หรือมี error จะแสดงข้อความสถานะและ fallback ภาพจำลอง
- มีปุ่มลองเปิดกล้องอีกครั้ง
- เมื่อออกจากหน้า play หรือเปลี่ยนกลับไปหน้า setup ระบบหยุด camera tracks เพื่อคืนกล้องให้อุปกรณ์

ข้อจำกัดตอนนี้:

- Hand tracking ยังเป็น overlay จำลอง
- ยังไม่เลือกกล้องหน้า/หลังจาก UI จริง มีเพียง default ตาม `playSurface`
- ยังไม่บันทึก permission state ระยะยาว
- ยังไม่ได้ส่งสถานะกล้องผ่าน socket ให้ครูเห็น

เกณฑ์จบ Local Camera:

- เปิด `/qa/ar-quest` บน `localhost` แล้วเข้า preview ต้องเห็น browser ขอสิทธิ์กล้อง
- เมื่ออนุญาต กล้องจริงต้องแสดงใต้ HUD/โจทย์/ตัวเลือก
- เมื่อปฏิเสธ ต้องเห็นข้อความอธิบายและปุ่มลองใหม่
- TypeScript ผ่าน
- i18n check ไม่มีรายการใหม่จากไฟล์ AR Quest

## สถานะ Hand Tracking

สิ่งที่ทำแล้ว:

- เพิ่ม hand pointer overlay ที่ขยับตาม mouse/touch บนพื้นที่กล้อง
- ตรวจจับการ hover เหนือคำตอบจากตำแหน่ง pointer
- กดค้างบนคำตอบเพื่อจำลอง gesture แบบ `pinch`
- เมื่อค้างครบเวลาที่กำหนด ระบบเปลี่ยนเป็นสถานะ lock answer
- สถานะด้านล่างเปลี่ยนตาม `open`, `hover`, `pinch`, `locked`
- ยังใช้ hand skeleton แบบ mock เพื่อให้ UX ใกล้กับ hand tracking จริง

ข้อจำกัดตอนนี้:

- ยังไม่ได้ใช้ MediaPipe หรือ hand landmark model จริง
- ยังไม่อ่าน landmark จากภาพกล้อง
- ยังไม่ส่งคำตอบที่ lock แล้วผ่าน socket
- ยังไม่มี calibration ระหว่างพิกัดกล้องกับพิกัดหน้าจอ

เกณฑ์จบ Hand Tracking prototype:

- เลื่อน mouse/touch บนหน้ากล้องแล้ว hand pointer เคลื่อนที่ตาม
- วาง pointer เหนือคำตอบแล้ว target แสดงสถานะกำลังเล็ง
- กดค้างบนคำตอบแล้ว target ถูก lock
- UI ยังไม่ทับโจทย์หรือ HUD บน mobile
- TypeScript ผ่าน
- i18n check ไม่มีรายการใหม่จากไฟล์ AR Quest
